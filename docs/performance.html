What Betty Actually Catches

Both bundled models, four languages, roughly a hundred errors planted at known offsets in each. Every number on this page comes from a benchmark anyone with the repository can re-run — including the ones that are not flattering.

← How it works · English · Danish · German · Spanish · Measured 7 September 2026

How to read this

A copy editor is judged on two things that pull against each other. Recall is the share of real errors it found. Precision is the share of its suggestions that were real errors. Pushing either one up tends to push the other down, and a tool that flags everything scores brilliantly on the first and is useless.

There is a third number, and in practice it is the one to read first: flags on clean text. Each language's fixture comes in two versions — one with errors planted, one with none. What a model says about the clean one is what an author actually experiences as noise, because there is nothing there to find. A tool that misses errors is disappointing. A tool that invents them makes the author distrust every suggestion, including the good ones.

The fixtures

Four texts of about 2,270 words each — the same short story, written natively in each language rather than translated, so the errors are the ones that language actually makes. Roughly a hundred errors per language are then planted by a generator that refuses any edit which does not produce exactly one span of the intended kind. The ground truth is therefore constructed, not annotated after the fact, so it cannot drift from the text.

Every task is run twice per model and the results averaged, which is enough to damp a single unlucky roll and not enough for a confidence interval. Treat a gap under roughly ten points between the two models as noise. One repeat is certainly not enough: a single-repeat run reported a prompt change as +10 points on both models that two repeats then measured at +11 on one and −3 on the other.

Copy edit, by language

The headline pair. Recall first, then precision — read them together, because either alone is easy to game.

It is almost entirely commas

Pooling every planted error that neither model found, across all four languages, gives the single most useful chart on this page.

Commas are 65% of everything missed — several times the next category. Nothing else on the list is close, and that is not because commas are unusually hard to see. It is because almost nothing deterministic is looking for them: the grammar server covers a handful of the English comma errors and a third of the German ones, and none at all in Danish or Spanish.

What was tried, and the one finding worth keeping

Comma rules were written into the model's prompt for two languages, and the contrast between them is more useful than either result.

Danish worked, on one model. The larger model's Danish comma recall went from 9% to 20% on the run that introduced the directives. Spanish did not move at all, on either model, from directives written with the same care: 5% → 4% and 11% → 8%.

Be careful how much weight that carries. The Danish figure has since drifted back into the high teens on a later run, and the smaller model never moved at all. It is one model gaining ten points on one category, which is roughly the size of the run-to-run noise these two repeats can resolve — a real effect, and a small one.

The difference is not the language, it is the shape of the rule. The Danish rules name a closed set of trigger words: put a comma before at, som, fordi, hvis, da, når, der. A model can pattern-match that. The Spanish rules describe a syntactic relation — bracket a parenthetical, separate an apposition — and there is no word to match on. Checking the fixtures confirmed it: exactly one of thirty Spanish missing-comma plants sits before a trigger word; the other twenty-nine are appositions and enumerations.

So the rule for adding comma support to a new language is: name the trigger words, or expect nothing. Where the comma depends on recognising a parenthetical, a 4-billion-parameter model will not find it however the instruction is phrased — and that is not a prompt-engineering problem worth retrying.

Line edit

Line editing is scored the same way — planted style errors, recall and precision — and the numbers are much lower. Some of that is real and some of it is the measurement, and it is worth being clear about which.

A "false positive" in the clean column is a suggestion that no planted error asked for — which for a line edit is very often just a line edit. Asked to improve the rhythm of a paragraph that contains no mistakes, a good editor still has opinions. The planted-error frame measures whether the model found the specific clumsiness that was deliberately introduced; it says nothing about whether the other suggestions were good.

A reference-free quality metric that does answer that question — perplexity reduction gated by an edit-distance ceiling, in the shape of the published Scribendi Score — is implemented and unit-tested in the codebase, but is not yet wired into this benchmark. The line-edit numbers here are the planted-error scores, and should be read as a floor rather than a verdict.

Translation

Translation has something copy editing does not: a human reference to compare against. The source text is translated into each language, and the result scored by chrF — character n-gram overlap with a human translation of the same passage, the standard automatic metric for this — plus two checks chrF is blind to.

chrF and chrF++ are 0–100, higher is better. len is output length over reference length. leak is the share of words left in the source language.

Both models land in the low-to-mid 70s, which for chrF is a serviceable translation rather than a publishable one. The larger model leads in all three target languages, though by very different amounts — nearly three points into German, two and a half into Danish, and barely half a point into Spanish.

The length and leak columns exist because chrF is easy to fool. A translation that stops early, or that leaves a proper noun and a handful of idioms in English, can still score well on character overlap; a reader notices both immediately. Length ratios here sit within a few percent of 1.00 and leakage under 2%, so in this case chrF is measuring what it looks like it is measuring.

The paragraph-level fluency reviewer that runs inside the real translation pass is scored separately, by a model judging translated paragraphs 1–5. It flagged six of ten paragraphs on the smaller model's Danish output — garbled words, an invented "his father" for "her father" — and none on the larger model's. That reviewer's job in production is to catch exactly those and re-translate them.

Betty in the Cloud, and what is not measured

Everything above is the two bundled local models. The paid cloud option runs a much larger model — Meta-Llama-3.3-70B on OVHcloud AI Endpoints — through the same pipeline, and it has not been through this four-language benchmark. It has been measured once, on English only, as part of choosing which model to run.

A seventy-billion-parameter model scoring level with a four-billion one is the result, and it is worth sitting with rather than explaining away. The categories say why: the deterministic layer does the spelling in both cases, and commas — the largest remaining pool — are not a capacity problem. The 70B was still the right choice among the five cloud models tested; it led the next best on recall by twenty-one points and on clean-text false positives by a factor of twenty, at half the token price. It just does not lead the local models by anything like its size.

Read that row as indicative, not settled. It is one run, one language, against the two-repeat four-language numbers everywhere else on this page — and one model in that same comparison varied by six points of recall across three runs. Running the cloud model through the full four-language benchmark is straightforward (scripts/test-models.ts --api) and costs well under a euro in tokens; it has not been done because the hosted service is not deployed yet.

What was fixed, and what it teaches

Four bugs found by this benchmark, listed because they share a shape worth recognising: a heuristic that is correct in English, silently wrong in one other language, and invisible until a large fixture exists in that language.

  • Spanish — the grammar server rewrote every quotation mark. One rule converted straight quotes to angled ones: 248 flags across the corpus, not one of them on a real error. Precision went from 31% to 67% and clean-text false positives from 71 to zero. One line of code.
  • Danish — a third of the dictionary was unreadable. 26,232 entries carried optional annotations the old spell checker did not strip, so den, havde and kom were all unknown words. Clean-text flags fell from 34 to 3.
  • German — the spell checker rejected 87,955 words from its own dictionary. Not a content gap. German capitalises every noun, so kommen collided with Kommen and the old checker kept only one of each pair. Danish loses one such pair in 1,240; English and Spanish lose none, which is why nobody had noticed.
  • German — every capitalised typo was protected as a name. The pipeline guards mid-sentence capitals as probable proper nouns, which is right in English, Danish and Spanish and describes every noun in German. It was discarding all 27 capitalised planted misspellings before the dictionary was ever consulted, even though the dictionary rejected all 44. Replacing the signal with recurrence — a character's name comes back, a typo does not — took German misspelling recall from 49% to 68% and overall German recall from 59% to 67%, with no change in any other language.

A related result, recorded because it saved work rather than created it: the dictionaries are all already current. Compared byte-for-byte against upstream, the German dictionary is the community frami build, the Danish one is Stavekontrolden 2.9.101, and English and Spanish match their upstream entry counts exactly. There is no dictionary upgrade available in any of the four — which moved the question from "get better data" to "use the data correctly", and that is where all four fixes above came from.

Is the bigger model worth it?

Mostly no, and it is better to say so.

Big Bad Betty costs roughly 30% more time and twice the memory, and the run scorecard puts the two models level. Split by language it gains three points of recall and three of precision — real, and not what twice the memory is usually expected to buy.

Where it does earn its size is narrow and specific: capitalisation (English 29% → 71%, German 79% → 93%, Spanish 80% → 100%), German commas (54% → 68%), and translation. It is level on spelling in every language. And it is worse on Danish — wrong-word recall halves, from 46% to 23% — which is the kind of result that makes a single headline number untrustworthy and is the reason this page splits everything by language.

This is the argument for spending effort on the deterministic layers rather than on recommending a bigger model: a dictionary fix or a disabled grammar rule helps both models equally, and helps the person running on an eight-gigabyte laptop most of all.

Reproducing this

Everything here comes from scripts/test-models.ts and scripts/test-translation.ts, run against the fixtures in sample_texts/. Results land in sample_texts/benchmark_results.json and its rendered .txt report, which includes every missed error and every false positive by name — that detail section is where all four of the fixes above were found.

The standing rule for changing a rule in this pipeline is the bar that found them: zero real errors found, at least one invented. Two of the four were caught by applying it to a rule nobody suspected. The ranked list of what is worth doing next lives in the repository as docs/language-quality-roadmap.md.
